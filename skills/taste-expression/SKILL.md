# Expression explores new directions with the user

Expression describes an approach for a task that explores a new direction, addresses a gap, or responds to a user correction. It interviews, explores, and iterates in the host conversation. Existing Pack guidance may still apply while exploring. Unresolved alternatives stay in the active task. The Pack is for durable product judgment and tested lessons that help future work, especially knowledge unlikely to be recovered by rereading code or reopening the screen; link to existing sources instead of copying their contents. When writing Pack guidance, preserve evidence and distinguish observed behavior, inference, and settled intent. Record settled rejected alternatives when they help explain a reusable decision. Resolved reusable feedback can update scoped guidance or create a minimal Pack for the affected surface after the host applies the change and keeps it only if checks show improvement or no regression. There is no persistent per-task activity state or separate promotion checkpoint.

The harness owns the agent loop and product workflow. Taste does not run tests or push changes. The host can self-check and maintain the Pack; no separate human review step is required.

## When to use this approach

Use Expression when the request asks for a new direction, surfaces unsupported product guidance, identifies a gap, or corrects an existing choice. Use Conformance when applying established, sourced guidance. Ask a focused clarification when the task or scope remains materially ambiguous. These are host judgments for the current task, not persisted Pack state.

## Work through the direction

1. If a Pack exists, inspect it and read guidance only for evidence-backed coverage relevant to this task/surface. If setup is `in_progress` or no Pack exists, do not use starter guidance; proceed with repository evidence and transient host-task context until the user feedback yields a clear reusable lesson.
2. Detect whether this task needs specialist craft beyond the Pack, such as visual composition, interaction design, UX flow, or product-decision elicitation. Check skills and plugins already available in the host. Use relevant installed capabilities according to the host's normal workflow; Taste does not rank them or require particular names.
3. If no suitable capability is already available, explain the gap and ask the user before searching the internet or installing anything. After search is approved, present relevant candidates and get approval for the chosen installation. The host performs discovery and installation; Taste supplies no shortlist and never installs silently. If the user declines, continue with the host's available capabilities and the Pack.
4. Try an approved capability on the current product task. Assess its usefulness on the artifact and workflow with the host's normal review. Keep trial results and feedback in the active host task; record useful operational learnings in the active task context.
5. Ask whether to keep a capability when the trial is complete. If the user wants to keep it, record its identity, version/source, and intended scope in a host-supported product or harness workflow location. The host owns that location and future activation. If no suitable persistent location exists, say the lock is session-only; do not put the catalog or lock in the Taste Pack.
6. When a meaningful UI tradeoff is unresolved, show concrete alternatives and explain their consequences. Ask a focused question about the outcome the user wants. Unresolved alternatives stay in the active task while designing and are not written into the Pack. When the user rejects a direction or corrects the host, treat that as direct evidence, revise the work, and note the settled rejection, the change, and the source in task context so a later guidance write can record why that alternative lost.
7. After resolving feedback, use judgment about whether it is worth carrying forward: is it likely to matter again, and is it hard to recover from the product or its sources? If so, save the concise lesson in the form that best conveys it. Link to code, docs, or rendered behavior rather than restating them. Cite evidence and distinguish observed behavior, inference, and settled intent. Keep unresolved alternatives and one-off reactions in the task. Do not use a fixed category list or save only failures.
8. When applying a UI fix or implementing the chosen direction, check and repair before accepting the edit. Run the product's existing checks and the relevant Pack checklist on the before state, then again after the edit. Keep the change only if the checker shows improvement or no regression. If the result regresses, revert and retry. Taste does not run these checks or own a CI gate. When local session tracing is enabled, follow `taste-design` and record the before and after check summaries on `taste_session_record` as `checkSummaries.before` and `checkSummaries.after`. If a usable Pack covers this surface, update the relevant guidance with `taste_pack_write`. For a new surface in an existing usable Pack, add the narrowly scoped guidance and a matching coverage entry, preserving the existing setup status, policy, scope, required coverage, and other coverage entries. Coverage may extend beyond the confirmed setup scope without changing what setup completion means. If no Pack exists, initialize a shell, replace its starter README and entry Skill, and record a one-surface `setupScope` and matching coverage as `usable_partial`. For an existing `in_progress` Pack, preserve the recorded scope and policy, or add a narrow scope if the shell has none. Replace starter content as needed and verify that the proposed `usable_partial` manifest passes validation. Link new guidance from the entry Skill or its routing reference and include it in the matching manifest coverage. Use `source_reviewed` by default and label visual behavior unverified unless you actually rendered it. Validate the Pack. Do not sweep unrelated routes or apps. If the result is only task-specific or evidence is insufficient, keep it in the conversation. No separate approval is needed for the evidence-backed lesson.
9. Report the change and the guidance or Pack created/updated. The user can correct the lesson in the same conversation; update it after applying the correction and keeping it only if the checker shows improvement or no regression. Offer `/taste-setup` when broader product coverage would be useful.

Do not create a Taste-owned skill shortlist, catalog, ranking, benchmark, or skill lock. Formal comparison/benchmarking is deferred until a product workflow has user-approved locked capabilities and there is evidence to measure.

For UI copy, use targeted clarity edits and preserve facts, constraints, and product voice. A phrase list or scanner match alone is not evidence that copy is wrong and does not authorize a rewrite.

After a successful Pack update, report the guidance references updated.
