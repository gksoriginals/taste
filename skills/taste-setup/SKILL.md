# Explicitly set up Taste for a repository

This workflow runs only on explicit user invocation (for example `/taste-setup`) or a clear request to set up/update the Pack. A UI request, missing Pack, rejected design, or new learning alone does not start repository setup.

1. **Inspect before creating or changing files.** Identify the repository root and read applicable `AGENTS.md` and local instructions. Inspect existing `taste/` configuration, product/package manifests, app directories, navigation/routes, UI source, design systems, and docs. Determine likely products and user-facing surfaces. If no Pack and no product UI exist, do not initialize: explain there is nothing to sweep yet. A user-requested new product or surface can proceed as Expression work; run Setup after it exists. If first-time rendered UI is inaccessible, do not create a Pack from source alone; report what access is missing and how to resume. For an existing Pack, continue its review even if current UI access is incomplete, but report the gaps and do not claim a full refresh.
2. **Choose bounded scope from evidence.** If one product and a clear primary app/surface are obvious, proceed with that scope and state the choice. For a single product with many surfaces, use navigation and product docs to choose a representative central workflow and relevant states, not every screen. If multiple products/apps remain plausible and the choice materially changes the Pack, ask which to configure first. For shared product identity and design foundations, use one repository Pack and route to app/surface guidance. Use separate Packs only for genuinely independent products or repositories. Do not default to sweeping a large monorepo.
3. **Review existing Packs before refreshing.** Read the Pack and compare its guidance with the selected product surfaces. Identify missing, stale, conflicting, or unsupported guidance. Reuse useful content and update only claims supported by inspected evidence. For an existing complete Pack, do not change setup status during discovery; once refresh changes are ready to write, mark it incomplete first. A source-only or otherwise incomplete refresh must remain marked incomplete and its gaps must be reported.
4. **Create or resume safely.** For first-time setup, finish the bounded rendered UI sweep before calling `taste_pack_initialize`; initialize only when product UI was found and could be inspected. Then write the tailored Pack. If an existing Pack is marked incomplete, resume from its current contents; never initialize again or overwrite finished files. If inspection stops before a first Pack can be initialized, leave the repository untouched and report how to rerun `/taste-setup`. If creation, writing, or validation is interrupted after initialization, preserve files, keep `setupStatus: incomplete`, note the next step when possible, and report the resume path.
5. **Inspect and reconcile evidence.** Review representative rendered flows and reachable states plus their source for the selected product/app/surfaces. Correlate UI with routes, design systems, local instructions, and product-owned docs. Record inspected evidence, covered surfaces, and inaccessible states. If useful, split only bounded parts across host-supported tasks/agents; give workers a shared evidence format and no Pack-write authority. The host reconciles their results.
6. **Write only useful product guidance.** Derive the smallest useful set of entry guidance, references, surface maps, checklists, facts, and metadata from the evidence. Do not create a fixed catalog, generic boilerplate, or empty categories. Keep the Pack in the product repository. Setup never changes product UI.
7. **Self-check and finish honestly.** Check scope coverage, source traceability, accuracy, consistency, and usefulness. Replace starter text with product-specific content and update manifest surfaces. Set `setupStatus: complete` only if the scoped sweep was accessible, its guidance is written and self-checked, and validation passes. Otherwise keep it incomplete and report gaps. Call `taste_pack_validate` and `taste_pack_inspect`. Report chosen scope, inspected surfaces and sources, changed guidance, validation, and coverage gaps.
8. **Keep task routing separate.** Normal UI work routes by task and affected surface: Conformance applies established sourced guidance; Expression handles a new direction, gap, or user correction; ask a focused question only for material ambiguity. With no Pack, continue the requested task from repository evidence and offer Setup separately. New product/surface design can proceed in Expression whether or not a Pack exists. Never create or refresh a Pack as a side effect of ordinary UI work. Resolved reusable feedback can update a relevant checklist in an existing complete Pack after applying and self-checking it.

Do not change product UI as a side effect of setup or review. Do not claim rendered inspection when only source was available. Never store private user conversation details; generalize a reusable lesson and cite the relevant artifact/source.
