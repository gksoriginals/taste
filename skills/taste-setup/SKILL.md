# Explicitly set up Taste for a repository

This workflow runs only on explicit user invocation (for example `/taste-setup`) or a clear request to set up/update the Pack. A UI request, missing Pack, rejected design, or new learning alone does not start repository setup.

1. **Inspect before choosing scope or writing.** Identify the repo root, read applicable `AGENTS.md` and local instructions, and inspect existing `taste/`, manifests, app directories, docs, routes, navigation, UI source, and design systems. Discover likely design sources from docs, config, links, and host integrations (for example Figma). Treat design files as evidence of intent and the running product as evidence of current behavior. Figma is optional. If a relevant source exists but is inaccessible, ask for access only if it would materially improve this Pack's scope; continue without it when rendered product UI is sufficient. If no Pack and no product UI exist, do not initialize: explain there is nothing to sweep yet. A requested new product/surface can proceed as Expression work; run Setup after UI exists.
2. **Map scope before traversal.** Inventory likely products/apps, entry points, route definitions, navigation, and shared components. Group routes into meaningful user journeys; note important states such as empty, populated, validation-error, loading, and permission-denied. Choose a bounded representative scope. If multiple plausible products/apps remain and the choice materially changes Pack scope, ask which to configure first; otherwise state the chosen scope and proceed. Do not require every route to be visited before producing useful guidance.
3. **Review existing Packs before refreshing.** Read the Pack and compare guidance with the proposed scope. Identify missing, stale, conflicting, or unsupported guidance; preserve useful content and change only claims supported by new evidence. For an existing Pack, once the read-only review and scope choice are complete, mark setup incomplete before rendered inspection or refresh writes. If access is missing or setup is interrupted, keep it incomplete and report the resume path. For first-time setup, leave the repo untouched until rendered product UI is accessible and inspected.
4. **Handle authentication safely.** First check for public routes, demo access, and documented local seed/test workflows. Use a safe local test account or seeded data when available; never request production credentials or store passwords, tokens, or real personal data. If auth blocks important coverage, ask once for the missing access or a safe local route; prefer configured secret handling or user-operated local login over credentials pasted into chat. Continue on accessible surfaces and with source review if access remains unavailable; if some accessible UI supports useful guidance, create only that evidence-backed subset and mark authenticated coverage incomplete. Do not repeatedly ask for credentials.
5. **Inspect efficiently.** Use available browser automation or harness UI tools to traverse representative journeys and capture screenshots or accessibility snapshots at meaningful checkpoints. Do a broader route pass to spot uncovered areas and unexpected behavior, but inspect high-value journeys and distinct visual/interaction states deeply. Avoid duplicating evidence for routes sharing components and behavior. Record the sample and what it does not cover. Never describe source-only inspection as visual inspection. If useful, delegate bounded inventories without Pack-write authority; the host reconciles evidence.
6. **Correlate and label evidence.** Review relevant routes, components, shared primitives, tokens, validation/state logic, and product docs. Use source to explain rendered behavior and identify hard-to-reach states, not as proof of appearance or UX. Keep evidence types distinct: rendered observation, source-derived fact, external design reference, or inference. Attach source/link and last-checked date where useful; state confidence and coverage limits.
7. **Use operational memory carefully.** If the harness has a configured memory facility, it may retain startup steps, safe seed setup, route entry points, or access limitations. Add provenance and a last-verified date to facts that can go stale, and verify them before reuse. Do not create a second product-guidance store: the Pack is canonical, versioned product knowledge. Never save secrets, tokens, credentials, or real user data in the Pack or harness memory.
8. **Create, resume, and validate.** For first-time setup, do not initialize if no product UI exists or if none of the selected UI can be rendered. If some product UI is accessible but important authenticated coverage is blocked, create guidance only from accessible evidence, record the gap, and leave the Pack incomplete. Existing incomplete Packs resume from current files without reinitialization or overwriting finished work. When the chosen scope has sufficient rendered inspection and evidence-backed guidance is self-checked, tentatively set `setupStatus: complete` and call `taste_pack_validate`; if it fails, restore `incomplete`. If important access is missing or setup is interrupted, keep incomplete and give the resume path. Report scope, journeys/states inspected, evidence types, Pack changes, validation, and gaps.
9. **Keep task routing separate.** Normal UI work routes by task and surface: Conformance applies established sourced guidance; Expression handles a new direction, gap, or correction; ask a focused question only for material ambiguity. With no Pack, continue the requested task from repository evidence and offer Setup separately. New product/surface design proceeds in Expression whether or not a Pack exists. Ordinary UI work never creates/refreshes a Pack or triggers a sweep. Reusable user feedback can update a relevant checklist in an existing complete Pack after applying and self-checking it.

Do not change product UI as a side effect of setup or review. Do not claim rendered inspection when only source was available. Never store private user conversation details; generalize a reusable lesson and cite the relevant artifact/source.
