# Initialize a Taste Pack at the right checkpoint

The harness coding agent performs setup. This plugin is already the Taste install. Do not configure or host another agent, daemon, or CI gate.

1. Identify the target product repository. If `taste/` exists, call `taste_pack_inspect` and continue it. Never overwrite it.
2. For a new Pack, bootstrap from the whole product rather than initializing an empty folder first. Inventory every user-facing surface from routes, navigation, source, and product-owned docs. Map core flows and reachable states. Use the host's browser or computer tools to inspect rendered UI and capture evidence; correlate with source, Git history, design files, and reviews where available. Record dates, routes, viewports, states, evidence links, and coverage gaps. Do not claim visual inspection from source alone.
3. If the product has multiple surfaces or independent flows, the host may split discovery across its available tasks, Claude tasks, or cloud agents. Give each worker a bounded surface, shared evidence format, and no authority to write to the Pack. The host consolidates overlaps, contradictions, and gaps before drafting and writing the product-specific Pack.
4. Derive the Pack structure from the sweep. Identify which guidance categories are actually useful for this product and its surfaces; create only those product-specific references, surface maps, checklists, metadata, and optional exemplars/evals that evidence supports. Do not start from a fixed catalog or preserve categories that have no useful content. Keep one `product-design/SKILL.md` as the front door: resolve request mode from the user's verb and artifact, then route to only the relevant product-specific material. Keep reviews from becoming edits and copy tasks from broadening into redesigns. Exclude backend-only work without user-visible effects. Link to canonical component, design-system, accessibility, and interaction sources instead of copying them. Group related routes into meaningful product surfaces; create a focused reference or checklist when that group needs durable, reusable guidance, not a file for every URL. For every claim, identify its source and distinguish observed behavior from inference. Keep useful unknowns as explicit coverage gaps; do not create an empty coverage file if the entry Skill or surface map can track them clearly. Add shipped exemplars only when the repository contains a useful example. Add gates or eval fixtures only when the product already has reliable checks or repeatable evidence. Do not create `AGENTS.md`, tooling scripts, or empty example files just to match another repository's tree. Do not leave boilerplate instructions presented as product-specific knowledge.
5. The host agent reviews its own sweep and Pack draft for coverage, source traceability, factual accuracy, consistency, and actionable guidance. No developer or other human review/approval stage is required. Initialize the Pack after this self-review, write the tailored references and checklists, validate the Pack, and summarize what was inspected and where evidence is incomplete. The user remains part of the normal design conversation: their correction, rejection, or disagreement is direct product evidence. Iterate on it, then update the relevant checklist automatically without asking for separate Pack or Decision approval. Never store private conversation details; generalize the user-facing lesson and cite the task or artifact that supports it.
6. For a greenfield surface or new requirement without shipped evidence, use transient Expression. As direct feedback resolves during the normal task, write reusable lessons to the relevant checklist after the host self-checks the change; no separate promotion checkpoint is required. Initialization creates one shared Pack; it does not create separate Conformance and Expression trees or edit `AGENTS.md` or harness config.
7. After initialization and content writes, call `taste_pack_validate`, then `taste_part_state` with `taskIntent: inspect_only`. Summarize the inspected surfaces, sources and states actually reviewed, checklist guidance created or updated, and open coverage gaps. When setup was triggered by a first UI task, continue that original task with the tailored Pack before reporting completion. Tell the user the Pack lives in the product repo at `taste/`.

A Pack with no structured Decisions may still contain useful surface references and checklists; the host should load those for the relevant task. Do not mark a Pack Conformance because files exist. Do not present generic starter content as a completed product sweep. Do not author a `supportedModes` field. Legacy Packs that still have split reference folders remain readable.
