# Explicitly set up Taste for a repository

Setup is a repository-wide workflow, separate from ordinary UI tasks. A missing Pack, routine request, or new design direction never starts a broad sweep implicitly. A resolved correction can still create a minimal Pack for its own surface through `taste-expression` when it establishes a clear reusable lesson. The host owns repository inspection, access, scope questions, evidence review, writes, and resumption; Taste supplies this workflow and Pack format.

1. **Inspect before choosing scope or writing.** Identify the repository root and local instructions. Independently inventory user-facing apps, routes, entry points, navigation, journeys, UI source, design systems, docs, integrations, and the existing Pack. A starter Pack's listed surfaces are hints only; compare them with repository evidence and detect omissions. Discover relevant design sources through docs/config/links and available integrations. They are optional evidence of intended design; the running product shows current behavior. Ask for design-source access only when it materially improves the agreed scope. If no product UI or UI source exists, do not create a generic Pack; explain that Setup can resume once a surface exists. New-product design can proceed as Expression.
   - **Find how to run the product.** Before any rendering, collect the documented way to start each app and sign in locally. Look in:
     - README run sections and repository instructions (`AGENTS.md`, `CLAUDE.md`);
     - package scripts, `docker-compose`/`Procfile`/`Makefile`, and dev-server launch configs (for example `.claude/launch.json`, `.vscode/launch.json`);
     - seed scripts and example env files that name local test accounts;
     - the host harness's own memory or notes for this repository.

     Those notes often hold the working recipe and its traps. Read the notes themselves, not only an index of them.
   - **Find the repository's guidance authorities.** Look for design-system docs, a team knowledge library or tool named in the instructions, or a product wiki. Record in the Pack which source wins on conflict and what each source owns. Keep the Pack focused on product judgment and tested lessons that help future work; link to code, lint, docs, existing instructions, or rendered behavior when those sources already provide the information.
   - **Find existing product decisions, not just run recipes.** Check repository instructions and design docs, available design/review integrations, relevant PR or issue feedback, and harness memories or notes for this repository—including feedback memories and rejected UI directions. Read only sources available to the current host and relevant to the agreed product scope. Record sources checked and access gaps in the setup report. Do not copy raw transcripts, private quotes, secrets, or personal data. Distill useful decisions into candidate lessons with rationale, scope, exceptions, rejected alternatives, and provenance; observed UI alone does not establish owner intent.
2. **Choose and confirm a useful review scope.** Inventory broadly to find likely gaps, but do not turn the inventory into Pack content. Select representative, consequential journeys where product judgment is likely to matter. If the user asks for the whole product, include all apps in the inventory, but do not require a guidance file or manifest row for every route. Show material scope choices and consequential journeys proposed for exclusion; `complete` requires user-confirmed scope, not a host-selected sample. Set `requiredCoverage` to the representative journeys agreed for this setup and `requiredStates` to the states that need to be rendered (default `["populated"]`). Keep the broader route inventory, “checked with no reusable lesson” notes, and unselected findings in the setup report, not the Pack.
3. **Review and resume safely.** Read an existing Pack before changing it. Run `taste_pack_inspect` and follow its `migrationNeeded` steps when an older Pack lacks current fields. A legacy `incomplete` status means `in_progress`. Find stale, duplicated, low-value, or unsupported guidance and remove material that is re-readable, volatile, or not useful across tasks; preserve verified lessons and links. Incomplete starter surfaces do not narrow scope. Do not overwrite finished guidance without checking it. Track setup status and retained guidance coverage separately. Preserve the most accurate status if interrupted and give `/taste-setup` as the resume path.
4. **Start the product before calling anything blocked.** A stopped local dependency is a step to take, not a gap to record. Examples: a container runtime or daemon, a local database, a dev server, a backend the UI calls.
   - **Run what step 1 found.** Start the stopped services through the documented recipe. Local, reversible start commands are in scope for setup.
   - **Sign in with the repository's local test identities.** Use documented test accounts, fixed-OTP users or seed scripts, and seed realistic non-sensitive data. These are expected and are not production credentials. Never request production credentials or store credentials, tokens, or real personal data, and never copy a test account's secret into the Pack.
   - **An existing local session counts, but say so.** A signed-in session already present in the harness browser may be used for a local or test environment; record that you used it.
   - **A dead backend is not populated coverage.** A UI that renders only loading, empty, or failure states because its backend is down has not been inspected with data. Keep starting things until populated states render, or until the attempts are exhausted.
   - **Only then record a block.** Record a journey as `blocked` only after these attempts fail. List each attempt and its result in that coverage entry's `accessAttempts`. For a required journey left `not_inspected`, record attempts too, unless you explain why trying was unsafe or out of scope. Do not use `not_inspected` to avoid an available, safe attempt. If important access is still missing, ask once for safe access when it materially improves coverage. Then continue with other in-scope apps and source review. Record the blocked journey, reason, missing evidence, and resume path.
5. **Inspect efficiently and accurately.** Use browser automation or harness UI tools for the selected representative journeys and meaningful states: populated, empty, loading, validation-error, permission-denied and offline, as applicable. Inspect broadly enough to catch important omissions, but do not persist a route-by-route log in the Pack. Keep “checked, no reusable lesson” and defects in the setup report; only durable guidance and the evidence needed to scope it belong in the Pack.
   - **Native and desktop apps.** Build and run them in the harness simulator, emulator or app-preview tools with the same local test sign-in. Use screen tools as well as source.
   - **Coverage.** Do a broader route pass for omissions without manually touring every URL. For each rendered coverage entry, list in `statesObserved` exactly which states you saw.
   - **Correlation.** Correlate routes, components, shared primitives, tokens, validation/state logic, docs, and design references.
   - **Evidence labels.** Label evidence `rendered`, `source_reviewed`, `design_reference`, or `inference`. Source review can support specific implementation guidance but never proves rendered appearance or UX. A `source_reviewed` reference is a repository-relative file path (optionally `:line`) that exists; put descriptions in `note`.
   - **Citations.** Cite traceable sources, dates, and sample limits. For each saved lesson, make its basis clear as an owner decision, observed behavior, or inference, and cite the source that supports that basis.
   - **Blocked apps.** A blocked app must not stop work on accessible surfaces.
6. **Review candidates and choose what is worth remembering.** Present decision candidates and material uncertainties in one concise batch when the user is available; let them confirm, edit, or reject candidates before recording them as owner decisions. If confirmation is unavailable, omit unsupported intent or label it as inference. A Pack captures durable product judgment. Saving an item predicts that future work will need it. Use judgment: is the lesson likely to recur or change a consequential decision? Would the future agent who needs it be able to retrieve it cheaply in its actual working context? Link to code, docs, lint, instructions, or UI when that same future agent can readily access the information there. If a durable decision is buried in a local-only memory or other inaccessible source, preserve a concise, generalized version in the shared Pack even if it duplicates the local source. Preserve concise lessons and a small index linking to them. Leave readily visible state, inventories, routine defects, and startup recipes in the UI, audit report, or operational notes. Distinguish owner decisions, observed behavior, and inference; cite provenance and add context when facts may drift. Include rationale, rejected options, and exceptions where they help future work. Never store credentials, tokens, private quotes, or real personal data. This is a purpose, not a fixed taxonomy, quota, or “failures only” rule. Evaluation fixtures and rubrics are optional; add them when a concrete evaluation is planned.
7. **Set status and validate.** `in_progress` means no surface yet has actionable, cited guidance meeting `setupPolicy.minimumUsableEvidence`. `usable_partial` means at least one covered surface meets it; apply that guidance only to its listed coverage and report remaining gaps. The default policy is `source_reviewed`: relevant UI source/docs, specific cited guidance, and an explicit note that visual behavior is unverified can qualify. `rendered_flow` additionally requires a representative rendered journey for the covered surface. Do not add per-surface evidence thresholds. `complete` means every ID in the user-confirmed `setupScope.requiredCoverage` has rendered and source-correlated evidence with cited guidance, has rendered every state in `setupScope.requiredStates`, the coverage target is met, host self-review passes, and `taste_pack_validate` passes. A host-selected sample cannot be marked complete. If validation fails, keep or restore the most accurate non-complete status. Treat validation warnings as work items, not noise. In particular, "no populated state rendered" means step 4 is unfinished.
8. **Report honestly.** Report:
   - chosen scope and independently inventoried apps;
   - decision sources checked, inaccessible sources, candidate decisions, and which candidates were confirmed, omitted, or labeled inference (without recording private source text);
   - how each app was started and signed in, or what was attempted;
   - representative journeys inspected, their `statesObserved`, and important findings (including surfaces checked with no reusable lesson);
   - guidance created/updated, audit findings separately with suggested issue titles, and operational notes separately;
   - status, validation result and warnings;
   - inaccessible or uninspected coverage, and how to resume.
   - During a Taste evaluation, save a redacted discovery record under `.taste-setup-runs/` (gitignored) with the repository revision, source categories checked and access gaps, candidate dispositions, confirmed scope, Pack changes, validation result, and deviations. Do not include private source text.

   Say plainly whether any populated state was rendered. Never call source-only work rendered or a scaffold complete. When session tracing is enabled, record the setup run with `taste_session_record`.
9. **Keep task routing separate.** Normal UI work uses existing evidence-backed coverage when available. Conformance applies established sourced guidance. Expression handles a new direction, gap, or correction whether a Pack exists or not. A clear reusable lesson can update scoped guidance or create a small `usable_partial` Pack scoped to the affected surface, without starting Setup. Keep one-off reactions and unresolved alternatives in the conversation. Preserve evidence and include rationale or rejected options when they add durable knowledge; do not add sections just to satisfy a template. Only `/taste-setup` starts a broader repository sweep.

Do not change product UI as a side effect of setup or review. Do not claim inspection that did not happen. Generalize reusable lessons without storing private conversation details.
