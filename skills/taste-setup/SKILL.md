# Explicitly set up Taste for a repository

Setup is a repository-wide workflow, separate from ordinary UI tasks. A missing Pack, routine request, or new design direction never starts a broad sweep implicitly. A resolved correction can still create a minimal Pack for its own surface through `taste-expression` when it establishes a clear reusable lesson. The host owns repository inspection, access, scope questions, evidence review, writes, and resumption; Taste supplies this workflow and Pack format.

1. **Inspect before choosing scope or writing.** Identify the repository root and local instructions. Independently inventory user-facing apps, routes, entry points, navigation, journeys, UI source, design systems, docs, integrations, and the existing Pack. A starter Pack's listed surfaces are hints only; compare them with repository evidence and detect omissions. Discover relevant design sources through docs/config/links and available integrations. They are optional evidence of intended design; the running product shows current behavior. Ask for design-source access only when it materially improves the agreed scope. If no product UI or UI source exists, do not create a generic Pack; explain that Setup can resume once a surface exists. New-product design can proceed as Expression.
   - **Find how to run the product.** Before any rendering, collect the documented way to start each app and sign in locally. Look in:
     - README run sections and repository instructions (`AGENTS.md`, `CLAUDE.md`);
     - package scripts, `docker-compose`/`Procfile`/`Makefile`, and dev-server launch configs (for example `.claude/launch.json`, `.vscode/launch.json`);
     - seed scripts and example env files that name local test accounts;
     - the host harness's own memory or notes for this repository.

     Those notes often hold the working recipe and its traps. Read the notes themselves, not only an index of them.
   - **Find the repository's guidance authorities.** Look for design-system docs, a team knowledge library or tool named in the instructions, or a product wiki. Record in the Pack which source wins on conflict and what each source owns. Keep the Pack focused on product judgment and tested lessons that help future work; link to code, lint, docs, existing instructions, or rendered behavior when those sources already provide the information.
2. **Choose and record a bounded scope.** If the user asks for the whole product/platform, include all apps that share its product identity and use one repository Pack with app/surface-specific routing. If multiple plausible products/apps remain and the choice materially changes scope, ask which to configure first. Otherwise state a reasonable scope and proceed. When the user did not name a scope and the selected scope spans more than one app, state it in one line before the sweep. If the user is present, give them the chance to narrow it (record `user_confirmed`); otherwise record `host_selected`. Record independently inventoried apps, selected products, exclusions, whether scope was host-selected or user-confirmed, required coverage, the coverage target, and `setupScope.requiredStates` (the UI states each required entry must render; default `["populated"]`). Judge completion against that recorded scope, not automatically the whole repository.
3. **Review and resume safely.** Read an existing Pack before changing it. Run `taste_pack_inspect` and follow its `migrationNeeded` steps when an older Pack lacks current fields. A legacy `incomplete` status means `in_progress`. Find stale, missing, conflicting, or unsupported guidance and preserve useful content. Incomplete starter surfaces do not narrow scope. Do not overwrite finished guidance. Track setup status and coverage as distinct fields. Preserve the most accurate status if interrupted and give `/taste-setup` as the resume path.
4. **Start the product before calling anything blocked.** A stopped local dependency is a step to take, not a gap to record. Examples: a container runtime or daemon, a local database, a dev server, a backend the UI calls.
   - **Run what step 1 found.** Start the stopped services through the documented recipe. Local, reversible start commands are in scope for setup.
   - **Sign in with the repository's local test identities.** Use documented test accounts, fixed-OTP users or seed scripts, and seed realistic non-sensitive data. These are expected and are not production credentials. Never request production credentials or store credentials, tokens, or real personal data, and never copy a test account's secret into the Pack.
   - **An existing local session counts, but say so.** A signed-in session already present in the harness browser may be used for a local or test environment; record that you used it.
   - **A dead backend is not populated coverage.** A UI that renders only loading, empty, or failure states because its backend is down has not been inspected with data. Keep starting things until populated states render, or until the attempts are exhausted.
   - **Only then record a block.** Record a journey as `blocked` only after these attempts fail. List each attempt and its result in that coverage entry's `accessAttempts`. For a required journey left `not_inspected`, record attempts too, unless you explain why trying was unsafe or out of scope. Do not use `not_inspected` to avoid an available, safe attempt. If important access is still missing, ask once for safe access when it materially improves coverage. Then continue with other in-scope apps and source review. Record the blocked journey, reason, missing evidence, and resume path.
5. **Inspect efficiently and accurately.** Use browser automation or harness UI tools for representative rendered journeys and meaningful states: populated, empty, loading, validation-error, permission-denied and offline, as applicable.
   - **Native and desktop apps.** Build and run them in the harness simulator, emulator or app-preview tools with the same local test sign-in. Use screen tools as well as source.
   - **Coverage.** Do a broader route pass for omissions without manually touring every URL. For each rendered coverage entry, list in `statesObserved` exactly which states you saw.
   - **Correlation.** Correlate routes, components, shared primitives, tokens, validation/state logic, docs, and design references.
   - **Evidence labels.** Label evidence `rendered`, `source_reviewed`, `design_reference`, or `inference`. Source review can support specific implementation guidance but never proves rendered appearance or UX. A `source_reviewed` reference is a repository-relative file path (optionally `:line`) that exists; put descriptions in `note`.
   - **Citations.** Cite traceable sources, dates, and sample limits.
   - **Blocked apps.** A blocked app must not stop work on accessible surfaces.
6. **Write product-specific guidance.** A Pack is durable product judgment: decisions and their reasons, tested lessons, and traps discovered through use that a future assistant is unlikely to recover by rereading the code or reopening the screen. Link to code, lint, docs, existing instructions, or rendered behavior when those sources already provide the information. Preserve useful observations when they establish a reusable lesson; distinguish observed behavior, inference, and settled intent, and mark volatile details with context rather than presenting them as timeless rules. Do not turn an observed pattern into an intentional rule without evidence for its rationale. Batch unresolved candidate decisions into a concise question when the user is available; otherwise leave them out of guidance or label them as inference. Create only the smallest useful Skills, references, checklists, and metadata supported by evidence. Record the trigger, scope, why, exceptions, and evidence. Unresolved alternatives stay in the active task. Settled rejected alternatives — options that were considered and why they lost — may be recorded when they help explain a durable decision. Do not invent examples; cite product evidence (a rendered observation, source, design reference, or an explicit settled decision). A reference that only records facts or evidence, not a design decision, declares `taste-kind: facts` (or `evidence`) in its frontmatter. Avoid generic boilerplate, fixed reference catalogs, unsupported product rules, empty files, and product UI changes. Keep audit findings (defects and suggested issue titles) separate from Pack guidance; keep operational notes (startup, safe seed setup, routes, access limits) in harness memory with provenance and last-verified dates for facts that can go stale. Never store secrets or personal data there.
   - **Give the Pack something to measure.** For at least one usable surface, add a conformance fixture under `evals/conformance/fixtures/<id>/`: `task.md`, plus `before/` and `after/` built from a real product file. That gives `taste-evaluate` something to measure. Write `evals/rubric.md` from the guidance.
7. **Set status and validate.** `in_progress` means no surface yet has actionable, cited guidance meeting `setupPolicy.minimumUsableEvidence`. `usable_partial` means at least one covered surface meets it; apply that guidance only to its listed coverage and report remaining gaps. The default policy is `source_reviewed`: relevant UI source/docs, specific cited guidance, and an explicit note that visual behavior is unverified can qualify. `rendered_flow` additionally requires a representative rendered journey for the covered surface. Do not add per-surface evidence thresholds. `complete` means every ID in the confirmed `setupScope.requiredCoverage` has rendered and source-correlated evidence with cited guidance, has rendered every state in `setupScope.requiredStates`, the coverage target is met, host self-review passes, and `taste_pack_validate` passes. If validation fails, keep or restore the most accurate non-complete status. Treat validation warnings as work items, not noise. In particular, "no populated state rendered" means step 4 is unfinished.
8. **Report honestly.** Report:
   - chosen scope and independently inventoried apps;
   - how each app was started and signed in, or what was attempted;
   - inspected journeys and their `statesObserved`, sources, and evidence types;
   - guidance created/updated, audit findings separately with suggested issue titles, and operational notes separately;
   - status, validation result and warnings;
   - inaccessible or uninspected coverage, and how to resume.

   Say plainly whether any populated state was rendered. Never call source-only work rendered or a scaffold complete. When session tracing is enabled, record the setup run with `taste_session_record`.
9. **Keep task routing separate.** Normal UI work uses existing evidence-backed coverage when available. Conformance applies established sourced guidance. Expression handles a new direction, gap, or correction whether a Pack exists or not. A clear reusable lesson can update scoped guidance or create a small `usable_partial` Pack scoped to the affected surface, without starting Setup. Keep one-off reactions and unresolved alternatives in the conversation. When that lesson is written, include settled rejected alternatives and cited product evidence. Only `/taste-setup` starts a broader repository sweep.

Do not change product UI as a side effect of setup or review. Do not claim inspection that did not happen. Generalize reusable lessons without storing private conversation details.
