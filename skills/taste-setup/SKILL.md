# Explicitly set up Taste for a repository

Setup is a repository-wide workflow, separate from ordinary UI tasks. A missing Pack, routine request, or new design direction never starts a broad sweep implicitly. A resolved correction can still create a minimal Pack for its own surface through `taste-expression` when it establishes a clear reusable lesson. The host owns repository inspection, access, scope questions, evidence review, writes, and resumption; Taste supplies this workflow and Pack format.

1. **Inspect before choosing scope or writing.** Identify the repository root and local instructions. Independently inventory user-facing apps, routes, entry points, navigation, journeys, UI source, design systems, docs, integrations, and the existing Pack. A starter Pack's listed surfaces are hints only; compare them with repository evidence and detect omissions. Discover relevant design sources through docs/config/links and available integrations. They are optional evidence of intended design; the running product shows current behavior. Ask for design-source access only when it materially improves the agreed scope. If no product UI or UI source exists, do not create a generic Pack; explain that Setup can resume once a surface exists. New-product design can proceed as Expression.
2. **Choose and record a bounded scope.** If the user asks for the whole product/platform, include all apps that share its product identity and use one repository Pack with app/surface-specific routing. If multiple plausible products/apps remain and the choice materially changes scope, ask which to configure first. Otherwise state a reasonable scope and proceed. Record independently inventoried apps, selected products, exclusions, whether scope was host-selected or user-confirmed, required coverage, and its target. Judge completion against that recorded scope, not automatically the whole repository.
3. **Review and resume safely.** Read an existing Pack before changing it; find stale, missing, conflicting, or unsupported guidance and preserve useful content. Incomplete starter surfaces do not narrow scope. Do not overwrite finished guidance. Track setup status and coverage as distinct fields. Preserve the most accurate status if interrupted and give `/taste-setup` as the resume path.
4. **Handle access gaps without stopping independent work.** Check public/demo routes and documented safe local seeds first. Use non-sensitive seeded data. Never request production credentials or store credentials, tokens, or real personal data. If important access is missing, ask once for safe access when it materially improves coverage, then continue with other in-scope apps and source review. Record the blocked journey, reason, missing evidence, and resume path.
5. **Inspect efficiently and accurately.** Use browser automation or harness UI tools for representative rendered journeys and meaningful states (empty, populated, validation-error, loading, permission-denied as applicable). Do a broader route pass for omissions without manually touring every URL. Correlate routes, components, shared primitives, tokens, validation/state logic, docs, and design references. Label evidence `rendered`, `source_reviewed`, `design_reference`, or `inference`; source review can support specific implementation guidance but never proves rendered appearance or UX. Cite traceable sources, dates, and sample limits. A blocked app must not stop work on accessible surfaces.
6. **Write product-specific guidance.** Create only the smallest useful Skills, references, checklists, and metadata supported by evidence. Cite product-specific claims in their guidance files and scope each file to supported apps/surfaces. Record the trigger, scope, why, exceptions, and evidence. Unresolved alternatives stay in the active task. Settled rejected alternatives — options that were considered and why they lost — must be recorded in the guidance. Do not invent examples; cite product evidence (a rendered observation, source, design reference, or an explicit settled decision). Avoid generic boilerplate, fixed reference catalogs, unsupported product rules, empty files, and product UI changes. The Pack is canonical, versioned product guidance. Harness memory may contain only operational notes (startup, safe seed setup, routes, access limits), with provenance and last-verified dates for facts that can go stale. Never store secrets or personal data there.
7. **Set status and validate.** `in_progress` means no surface yet has actionable, cited guidance meeting `setupPolicy.minimumUsableEvidence`. `usable_partial` means at least one covered surface meets it; apply that guidance only to its listed coverage and report remaining gaps. The default policy is `source_reviewed`: relevant UI source/docs, specific cited guidance, and an explicit note that visual behavior is unverified can qualify. `rendered_flow` additionally requires a representative rendered journey for the covered surface. Do not add per-surface evidence thresholds. `complete` means every ID in the confirmed `setupScope.requiredCoverage` has rendered and source-correlated evidence with cited guidance, the coverage target is met, host self-review passes, and `taste_pack_validate` passes. If validation fails, keep or restore the most accurate non-complete status.
8. **Report honestly.** Report chosen scope, independently inventoried apps, inspected journeys/states and sources, evidence types, files created/updated, status, validation result, inaccessible or uninspected coverage, and how to resume. Never call source-only work rendered or a scaffold complete.
9. **Keep task routing separate.** Normal UI work uses existing evidence-backed coverage when available. Conformance applies established sourced guidance. Expression handles a new direction, gap, or correction whether a Pack exists or not. A clear reusable lesson can update scoped guidance or create a small `usable_partial` Pack scoped to the affected surface, without starting Setup. Keep one-off reactions and unresolved alternatives in the conversation. When that lesson is written, include settled rejected alternatives and cited product evidence. Only `/taste-setup` starts a broader repository sweep.

Do not change product UI as a side effect of setup or review. Do not claim inspection that did not happen. Generalize reusable lessons without storing private conversation details.
