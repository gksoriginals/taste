# Sweep an agreed product scope during explicit setup

The host gathers, reconciles, and self-checks evidence, then writes product-specific Skills, references, and checklists into the Pack. Structured Decision files are legacy and are not part of the routine sweep learning loop.

1. Run only when the user explicitly invokes `/taste-setup` or asks to sweep/refresh the Pack. Inspect repository instructions, manifests, apps, existing Pack, docs, route definitions, navigation, shared UI, and links/config pointing to Figma or other product design sources. Use available integrations if connected. Treat the running product as evidence of current behavior and external design files as evidence of intended design. Figma is optional; missing Figma access does not block viable product UI inspection. Ask for access to an otherwise-relevant design source only if it materially improves this scope.
2. Map scope before traversal. Inventory likely apps, entry points, routes, and navigation from the repository. Group routes into meaningful user journeys and identify important empty, populated, validation-error, loading, and permission-denied states. If several plausible apps/products would materially change Pack scope, ask which to configure first. Otherwise choose a bounded representative scope, state it, and proceed. Do not require every route to be manually visited.
3. Check authentication access. Look for public routes, demo modes, and documented local seed/test workflows first. Use a safe local test account and non-sensitive seeded data when available. Never request production credentials or save passwords, tokens, or real personal data. If auth blocks important coverage, ask once for missing access or another safe way into the local environment. If it remains blocked, continue accessible UI plus source review, record authenticated coverage as incomplete, and explain how to resume.
4. Inspect efficiently. Use browser automation or other host UI tools to traverse high-value journeys and capture screenshots/accessibility snapshots at meaningful checkpoints. Do a broader route pass to find unexpected behavior and uncovered areas, then inspect representative flows and distinct visual/interaction states deeply. Avoid duplicating inspection where routes share components and behavior. State what the sample does not cover. Source review alone never counts as rendered inspection. If you delegate bounded inventory, give workers a shared evidence format and no Pack-write authority; reconcile centrally.
5. Correlate evidence. Review relevant routes, components, shared primitives, design tokens, validation and state logic, and local docs. Use source to corroborate rendered behavior and find hard-to-reach states, not to claim appearance or UX. Label evidence as rendered observation, source-derived fact, external design reference, or inference. Attach traceable source references, confidence, and last-checked dates where appropriate. Avoid converting repeated implementation into an unsupported product rule.
6. Write the narrowest useful guidance. Create or update only Skills, references, checklists, and metadata justified by the evidence. Record inspected journeys/states, source references, inaccessible areas, and meaningful sample limits. Preserve useful existing Pack content and update only supported guidance. The host self-reviews traceability, coverage, accuracy, consistency, and usefulness; no separate human review stage is required. Do not create fixed catalogs, generic boilerplate, empty files, harness configuration, or product UI changes.
7. Manage status and resume honestly. For a first Pack, do not initialize if there is no product UI or none of the chosen UI can be rendered. If some selected UI is accessible but important auth coverage is blocked, create only evidence-backed guidance and leave `setupStatus: incomplete`. For an existing Pack, review it first, then mark incomplete before the refresh sweep or first change. Keep it incomplete when important access is missing, a sweep is interrupted, self-review fails, or validation fails. Once inspection and self-review are sufficient, tentatively set complete and run `taste_pack_validate`; restore incomplete on failure. Preserve completed files and report `/taste-setup` as the resume path.
8. Keep normal UI learning separate. Resolved reusable user feedback may update a relevant checklist in an existing complete Pack after applying and self-checking it. This does not trigger setup or a broad sweep. Without a complete Pack, keep learning in the active task until explicit setup.

Conformance and Expression are host-selected task approaches, not setup states or persistent Pack modes. Legacy structured Decision activity remains readable as compatibility data; it does not route checklist-based work.
