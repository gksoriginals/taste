# Sweep an agreed product scope during explicit setup

The host gathers, reconciles, and self-checks evidence, then writes product-specific Skills, references, and checklists into the Pack. Structured Decision files are legacy and are not part of the routine sweep learning loop.

1. Run only when the user explicitly invokes `/taste-setup` or asks to sweep/refresh the Pack. Inspect the repository root, local instructions, manifests, apps, UI surfaces, design systems, and existing `taste/` before choosing scope. If there is no product UI, do not create a Pack. If first-time rendered UI is inaccessible, stop before initialization and explain what is needed. For one product with a clear primary surface, choose it and state the choice; for one product with many surfaces, select a representative central workflow and states from navigation/docs. Ask which one first only when multiple plausible products/apps materially change scope. Keep broad monorepo discovery for scope selection only; inspect a bounded product/app scope.
2. Inspect representative rendered UI and source for the agreed scope, its important flows and reachable states. Capture enough evidence to support reusable product guidance and report inaccessible states. If useful, split the agreed bounded scope across host-supported tasks/agents; give workers a shared evidence format and prohibit Pack writes. The host reconciles findings.
3. Correlate rendered evidence with source, Git history, reviews, design files, and canonical product sources. Separate verified facts, observed patterns, inferences, and open questions. Do not infer that a repeated pattern is intentional from repetition alone. Report inaccessible surfaces and other coverage gaps. Never claim a screen was seen if it was not. Do not store private production data without authorization.
4. Consolidate an evidence-backed surface map and useful checklist items. Each item should state a concrete check, scope, source, rationale, exception, and confidence. Separate directly observed behavior from inferred intent; treat shipped patterns as useful evidence but not proof of universal policy. Record scope coverage and gaps in the setup report or a useful Pack file; do not create a standalone coverage file unless it adds value.
5. The host agent reviews its own sweep and draft for coverage, source traceability, factual accuracy, consistency, and actionable guidance. No separate developer or human review/approval stage is required. For first-time setup, finish rendered inspection of the agreed scope before initializing a Pack; if no product UI exists or it cannot be inspected, do not create a generic/source-only Pack. For an existing Pack, review content first, preserve useful guidance, and update only what evidence supports. If a refresh changes files, mark the Pack incomplete before the first write. Choose only useful product-specific guidance; do not populate a fixed catalog or create empty files. Update `manifest.json` with agreed surfaces and status. Write one concise entry Skill routing by task and surface to relevant product references and checklists. Add references, examples, gates, or evals only when evidence supports their value. Do not create harness files or generic boilerplate. Use `taste_pack_write` for guidance; `taste_record_signal` remains legacy. The host self-review is the quality check. Taste does not decide which product checks apply or run them.
6. During normal UI work, resolved reusable user feedback can update a relevant checklist in an existing complete Pack after the host applies and self-checks it. This does not trigger setup or a broad sweep. If no complete Pack exists, keep the learning in the active task until explicit setup is invoked. Set `setupStatus: complete` only when all scoped files are written and self-checked; then validate and inspect the Pack. If validation fails, restore `setupStatus: incomplete` before reporting. If interrupted, leave `setupStatus: incomplete`, preserve written files, note next steps when possible, and report that `/taste-setup` safely resumes from the existing Pack.

Legacy structured Decision activity is still derived from its stored evidence. Checklist guidance applies independently to each scoped task even when no structured Decision exists. Other parts retain their existing derived state.
