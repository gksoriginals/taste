# Design with the Pack

The coding harness owns the loop. Taste does not start an agent. Do not design product UI from memory when a Pack can be loaded.

1. Resolve the repository path and check for `<repo>/taste/`. If a Pack exists, inspect it and load only guidance relevant to this scope. Apply evidence-backed guidance for its listed coverage regardless of whether broader setup is complete. A `usable_partial` Pack is intentionally useful before the full sweep is complete. If setup is `in_progress`, ignore starter boilerplate and unsupported claims, but use any valid, evidence-backed guidance already recorded; continue the requested task and offer `/taste-setup` only for broader coverage.
2. If no Pack exists, do not start a product-wide sweep as a side effect of this UI request. Continue the requested work from repository evidence and available host capabilities. If feedback resolves into a clear, reusable lesson for the affected surface, use `taste-expression` to create a minimal, evidence-backed Pack for that surface. Use `/taste-setup` when the user wants a broader product sweep. A new direction, correction, or greenfield surface is Expression work and can proceed without a prior Pack.
3. Choose the path per part, not for the whole Pack:
   - Apply existing product guidance for the relevant scope.
   - Use **Expression** for a new direction, correction, gap, or greenfield task. Apply relevant existing guidance while exploring.
   - If a Pack covers the affected surface and the task yields a clear reusable lesson, update the relevant guidance after applying it and keeping the edit only if checks show improvement or no regression. If the surface is not covered, inspect relevant code and product evidence, then add only the reusable lesson and its evidence. Keep the essential rule and rationale in the Pack itself. Cite committed code surfaces by repository-relative path (and line or symbol when useful); a code link supports the rule but never replaces it. Copy important lessons from local or harness-specific sources into concise, generalized Pack guidance so they travel with the repository. Preserve provenance and uncertainty. Initialize a minimal Pack only when none exists. This is routine learning, not a product-wide setup. Unresolved alternatives stay in the conversation.
4. For Expression work that needs specialist visual, interaction, UX-flow, or product-decision craft beyond the Pack, follow `taste-expression`'s detect → ask-install → try → lock steps. The host discovers candidates and owns any approved installs and persistent locks; Taste has no required skill names, shortlist, or catalog.
5. Implement only when implementation is requested. For a review, report findings without editing unless the user separately asks for changes. For non-trivial UI work — layout, interaction, flow, or visual structure, rather than a typo or mechanical token swap — write a short task-local brief before editing product files. The brief states the intent, the Pack constraints that apply, and the options you are rejecting. Unresolved alternatives stay in that brief, not in the Pack. Use the harness browser, computer-use, or rendered preview when visual evidence matters.
6. Check and repair the edit with checks that already exist. Run the product's existing checks and the relevant Pack checklist before the change and again after it. For every task acceptance condition and applicable Pack constraint, record **Pass**, **Fail**, or **Unverified**, with the check or evidence. A blocked browser, unavailable tool, or missing baseline means **Unverified**; do not imply the condition passed. Repair failures when the available tools allow it. If a required condition cannot be verified or remains failed, report it as unresolved instead of presenting the implementation as fully checked. Keep the change only if checks show improvement or no regression; otherwise revert and retry. Do not add a Taste-owned test runner or CI gate.
7. Treat corrections, rejections, and disagreements in the live conversation as direct feedback. Revise only the requested UI scope, then run the same check-and-repair comparison. Update scoped Pack guidance or create a minimal surface-scoped Pack when the lesson is clear, reusable, and supported by the changed artifact or product evidence. Preserve the evidence and explain the judgment when that rationale helps a future task. Do not invent examples. Do not use feedback as a reason to sweep unrelated surfaces.
8. If the user corrects existing guidance, apply the correction and update it as part of the same task. If the affected surface is uncovered, create narrow guidance for it after the lesson is clear. Do not ask for separate Pack-write approval. Unresolved alternatives stay in the task context.
9. Report the guidance loaded or updated, what you actually inspected, and any remaining gaps. Summarize acceptance and Pack-check statuses as Pass/Fail/Unverified, and include evidence or the blocker for each unresolved item. If the task produced a usable partial Pack, state which surface it covers; offer `/taste-setup` for broader coverage.

## Session traces

When the Taste server reports that local tracing is enabled, generate a random UUID at the start of the task and pass it as `runId` on Taste MCP calls. Note the starting revision and any relevant changes already in the working tree. At the end, call `taste_session_record` with a short task and surface summary, guidance actually read and applied (including direct file reads), the decision and its reason, verification evidence, artifact references, and explicit user feedback if available. When you ran check-and-repair, include the before and after check summaries as `checkSummaries.before` and `checkSummaries.after`. Use `pending` when feedback is unavailable. If feedback arrives later in the same task, save another snapshot with the same run ID. Use short summaries and artifact references. Exclude secrets, personal data, and raw conversations. If tracing fails, report the gap and finish the product task.
