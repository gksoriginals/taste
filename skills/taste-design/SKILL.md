# Design with the Pack

The coding harness owns the loop. Taste does not start an agent. Do not design product UI from memory when a Pack can be loaded.

1. Resolve the product repository path from the harness and check whether `<repo>/taste/` exists. If it exists, call `taste_pack_inspect` and `taste_part_state` with a required `taskIntent` and affected `scope`: use `apply_existing` when following established guidance; use `new_direction`, `correction`, `gap`, `greenfield`, or `unclear` for the corresponding request. Read `skills/product-design/SKILL.md`, shared product facts, relevant surface references, and `references/checklists/` entries for the task. Apply relevant checklists even if `taste_part_state` reports Expression because no structured Decision exists. On a legacy Pack with split folders, read those references too.
2. If no Pack exists, this first UI request triggers bootstrap; the user does not need to ask separately for Taste setup. Determine whether the product already has user-facing UI. For an existing product, follow `taste-setup` / `taste-sweep` to inspect the whole product, derive its Pack contents from the evidence, self-review, and initialize/populate the Pack. Then resume and complete the original UI request using that Pack. For a genuinely greenfield product or surface, follow `taste-expression` and keep user input and iteration in the active host task; initialize a Pack when the task yields useful reusable product guidance. Do not create a generic or empty Pack merely to start either workflow.
3. Choose the path per part, not for the whole Pack:
   - Apply **product guidance** whenever a relevant surface reference or checklist exists, even if `taste_part_state` reports Expression because there are no legacy structured Decisions. Follow `taste-conformance` to use the checklist and canonical references.
   - Use **Expression** when `taste_part_state.taskRouting` says Expression or the user asks for a new direction, correction, gap resolution, or greenfield judgment. Apply existing checklists while exploring, then update the relevant checklist after self-checking a resolved reusable correction. A supplied `taskIntent` leaves legacy persisted Decision state unchanged. With an absent Pack, use `taste-sweep` for existing UI and `taste-expression` for greenfield UI.
4. For Expression work that needs specialist visual, interaction, UX-flow, or product-decision craft beyond the Pack, follow `taste-expression`'s detect → ask-install → try → lock steps. The host discovers candidates and owns any approved installs and persistent locks; Taste has no required skill names, shortlist, or catalog.
5. Implement or review only the requested scope. Use the harness browser, computer-use, or rendered preview when visual evidence matters. Run only mechanical checks that already exist in the product repo.
6. Treat corrections, rejections, and disagreements in the live conversation as direct feedback. Revise the UI within the user's task, self-check with available product workflows, then update the relevant checklist using `taste_pack_write` when the lesson is clear and reusable. Do not wait for final artifact approval or a separate promotion checkpoint.
7. If the user corrects a checklist entry, apply the correction and update it as part of the same task. Do not ask for separate Pack-write or Decision-text approval. Keep one-off or unresolved preferences in the task context.
8. Report the guidance and checklist entries loaded or updated, the derived activity per part, what you actually inspected, and any remaining gaps. On first-use bootstrap, also confirm that the original UI request was completed after creating the tailored Pack.

`taste_mode_resolve` is a deprecated helper. It does not read the Pack and it does not decide who initiates Expression. Pass the host-interpreted current request as `taskIntent` to `taste_part_state`; that tool returns the task-local Expression route alongside unchanged Pack-derived state. The tool cannot parse raw conversation text itself.
