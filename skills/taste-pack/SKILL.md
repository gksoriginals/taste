# Maintain one Pack

The harness coding agent interprets evidence. Taste tools read and write files inside the product repository's `taste/` directory.

## Where finalized judgment lives

Store durable product judgment in scoped references: decisions and reasons, tested lessons, and traps discovered through use. Put the essential rule, rationale, scope, and limits in the Pack so they remain usable across machines and harnesses; links are supporting evidence, not a substitute for guidance. Cite committed code surfaces by repository-relative path (and line or symbol when useful). If an important decision lives only in local memory or an inaccessible review source, preserve a concise, generalized version in the Pack even if that duplicates local knowledge. Discover feedback memories and decision notes as well as run recipes during explicit setup; do not copy raw private material. Preserve provenance and distinguish owner decisions, observed behavior, and inference; note context for facts that may change. Choose a form that teaches the judgment, such as a checklist, decision tree, or annotated example. Do not invent examples. Keep the product-design entry Skill focused on routing by task and surface. Link new references from that routing and list them in matching manifest coverage. During normal UI work, the host may update scoped guidance or add coverage for an uncovered surface while preserving existing setup scope, status, policy, and other coverage. The host may initialize a minimal Pack when no Pack exists and a clear reusable lesson has been applied and retained only if checks show improvement or no regression. No separate approval is needed. A broad product sweep still requires explicit user invocation of `/taste-setup`. During refresh, preserve the most accurate status as evidence changes; use `in_progress`, `usable_partial`, or `complete` according to validated evidence and user-confirmed scope before claiming completion. Conformance and Expression are task approaches, not Pack states.

Treat each saved item as a prediction about what future work will need. Keep concise, supported lessons that are hard to recover from the product or from sources readily available to the future agent; link to details that same agent can retrieve. Use judgment rather than a fixed taxonomy, quota, or “failures only” rule. Coverage should help retrieve retained guidance, not inventory routes.


## Update rules

- `taste_pack_initialize` creates an `in_progress`, non-overwriting shell and fails if `taste/` already exists. Use it during explicit `/taste-setup` after inventory, or during a normal UI task only after resolved user feedback yields a clear reusable lesson for a specific surface. For a feedback-created Pack, immediately replace starter text with scoped guidance and provenance, record only that surface as `usable_partial`, and validate; do not start a broader sweep. Do not initialize when no product UI or UI source exists. Source-only inspection can support `usable_partial` under the default `source_reviewed` policy when guidance is cited and visual behavior is explicitly unverified; `rendered_flow` requires a rendered representative journey. For broader refreshes, inspect the existing Pack first and preserve useful content. The shell is not a completed Pack and does not edit harness instructions.
- Inspect and validate before and after Pack maintenance. Follow `migrationNeeded` from `taste_pack_inspect` for older Packs (a legacy `incomplete` status means `in_progress`). Treat validation warnings as work items. `taste_pack_write` can edit checklists, facts, Skills, references, metadata, and fixtures inside `taste/`.
- Coverage fields that validation enforces:
  - a `source_reviewed` evidence reference is a repository-relative file path (optionally `:line`) that exists;
  - a `rendered` entry lists `statesObserved` from populated, empty, loading, error, denied, validation, offline;
  - a `blocked` entry lists the `accessAttempts` made before giving up;
  - `complete` requires every required entry to have rendered each state in `setupScope.requiredStates` (default populated).
- Unresolved alternatives stay in the active task, along with one-off reactions and private conversation details. Include rationale or rejected options when they preserve knowledge a future assistant would otherwise miss; do not add empty sections to satisfy a template. Cite evidence in the form that best supports retrieval, including committed code paths inside the guidance. When the task yields important reusable judgment, update covered guidance or add narrowly scoped guidance and coverage even when broader setup is absent or incomplete. Preserve the judgment, rationale, scope, and limits in the Pack; do not rely on a link or local memory to explain the rule. Distill important lessons from local-only sources into concise Pack content, even if that duplicates local knowledge. Keep broader setup status incomplete unless its own evidence and scope requirements are met. Do not store private user quotes or personal details.
- During explicit setup, batch material candidates from existing decision sources for owner confirmation before labeling them owner decisions. If unavailable, omit unsupported intent or label it inference. Normal UI work can still record a clear resolved user correction in the same task without a separate promotion checkpoint.
- Preserve uncertainty. One screenshot is not a universal rule.
- Route ordinary work from the user's task and affected product surface. Choose Conformance to apply established sourced guidance, Expression to explore a new direction or address a gap/correction, or clarify when intent or scope is materially unclear.

For evaluation fixtures, use `taste-evaluate`. Fixture lanes named conformance and expression are storage paths, not Pack modes.
